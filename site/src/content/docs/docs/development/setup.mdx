Contributions are welcome. Antimony is split into three repositories, and you usually work on the server and the interface side by side.

| Repository | Language | Run locally on |
| --- | --- | --- |
| [antimony-server](https://github.com/antimony-team/antimony-server) | Go | `localhost:3100` (API), `localhost:6767` (SSH) |
| [antimony-interface](https://github.com/antimony-team/antimony-interface) | React, TypeScript, Vite | `localhost:5173` |

The development ports differ from those of the [Docker deployment](/docs/deployment/docker/) (8080, 3000 and 6969), so both can run on the same machine.
| [antimony](https://github.com/antimony-team/antimony) | Astro, Starlight | `localhost:4321` (this documentation) |

## Server

### Prerequisites

- [Go](https://go.dev/) 1.26
- [Task](https://taskfile.dev/)
- [containerlab](https://containerlab.dev/install/) and Docker, for deploying real labs
- [golangci-lint](https://golangci-lint.run/) for linting

### Run it

```bash
git clone https://github.com/antimony-team/antimony-server
cd antimony-server

# PostgreSQL and a Keycloak instance for OpenID Connect
docker compose up -d

# Build and run with the test configuration
task run
```

`task run` builds the server into `build/`, copies `data/`, the test config (`test/config.test.yml`) and `test/kinds.conf.yml` next to it, and starts it with `sudo` in development mode. containerlab and packet capture need root.

The development `docker-compose.yaml` starts:

- **PostgreSQL 18** on port 5432. Its init script in `test/postgres` creates the `antimony` user with password `password123`.
- **Keycloak** on port 4022 with admin `admin` / `admin` and a realm imported from `test/keycloak`. The test configuration uses it as OpenID provider (`http://localhost:4022/realms/antimony`, admin group `antimony-admin`).

The admin login is `admin` / `admin`. After an OpenID login, Keycloak redirects back to `http://localhost:3100/users/login/success`, which the imported realm allows. If you change `openIdRedirectHost` in the test configuration, also change the client's redirect URI in Keycloak.

<Aside type="note" title="OpenID Connect on localhost">
	The browser and the server must reach the OpenID provider under the same URL. With Keycloak in a container and the server on the host, both use `localhost:4022`, which works. If you run the server in a container too, OpenID login generally won't work without extra network setup; use the admin login instead.
</Aside>

### Other tasks

| Task | What it does |
| --- | --- |
| `task build` | Builds the server into `build/` without running it. |
| `task run-c9s` | Runs with `test/config-c9s.test.yml`, using the clabernetes provider. |
| `task setup-kind` | Creates a local [kind](https://kind.sigs.k8s.io/) cluster named `c9s` and installs clabernetes 0.9.0. |
| `task build-docker` | Builds the Docker image `antimony-server:dev`. |
| `task run-docker` | Builds the image and runs it with SQLite and the Docker test configuration. |
| `task test` | Runs the tests. |
| `task test-race` | Runs the tests with the race detector, in random order. CI uses this. |
| `task test-coverage` | Runs the tests with a coverage report. |
| `task lint` / `task lint-fmt` | Lints or formats the code with golangci-lint. |
| `task swag` | Regenerates the Swagger documentation in `src/docs/`. |
| `task swag-check` | Fails if the committed Swagger documentation is outdated. CI uses this. |
| `task clean` | Removes `build/`. |

The integration tests in `src/test/` run the whole server in-process with the dummy provider and a test OpenID server, so they don't need Docker.

### API documentation

The REST API is documented with [swag](https://github.com/swaggo/swag) annotations on the handlers. After changing them, run `task swag` and commit `src/docs/`. A running server serves Swagger UI at `/swagger/index.html`.

## Interface

### Prerequisites

- [Node.js](https://nodejs.org/) 26
- [Yarn](https://classic.yarnpkg.com/) 1, for example through `corepack enable`
- [Task](https://taskfile.dev/installation/), for builds and Antimony Desktop. Some distributions install it as `go-task`.

### Run it

```bash
git clone https://github.com/antimony-team/antimony-interface
cd antimony-interface
yarn install
yarn start
```

The development server runs on [localhost:5173](http://localhost:5173). It forwards `/api` (without the prefix) and `/socket.io` to the development server of the backend on `localhost:3100`.

### Scripts and tasks

The everyday commands are Yarn scripts:

| Script | What it does |
| --- | --- |
| `yarn start` | Development server with hot reload. |
| `yarn build` | Production build into `dist/`. |
| `yarn test` | Runs the unit tests. |
| `yarn lint` | Lints with [gts](https://github.com/google/gts). |
| `yarn typecheck` | Type-checks without building. |
| `yarn e2e` | Runs the end-to-end tests. |

Everything that takes more than one step is a task in `Taskfile.yml`. Tasks install the dependencies when needed and skip builds whose inputs haven't changed. `task --list` shows them all.

| Task | What it does |
| --- | --- |
| `task check` | Lint, type check and unit tests in parallel. |
| `task build-dev` | Development build with source maps into `dist/`. |
| `task preview` | Builds and serves the production build. |
| `task build-docker` | Builds the Docker image `antimony-interface:dev`. |
| `task build-electron` | Builds [Antimony Desktop](/docs/deployment/desktop-app/) without packaging it. Start it with `yarn electron .`. |
| `task package-electron-linux` | Builds Antimony Desktop as AppImage, .deb and .rpm for x86_64 and ARM64 into `release/`. |
| `task e2e-ui` | Opens the end-to-end tests in Playwright's UI. |
| `task e2e-report` | Opens the report of the last end-to-end run. |
| `task clean` | Removes the build output. |

### Where the interface finds the server

The interface needs no configuration. In the browser, it calls `/api` and `/socket.io` on the address it was opened at, which the development server, the e2e preview and Traefik in the Docker deployment forward to the server. Antimony Desktop gets the address of the server it started at runtime.

To build an interface that talks to a server elsewhere, set these variables when building, for example `SB_API_SERVER_URL=https://lab.example.com/api yarn build`:

| Variable | Default | Description |
| --- | --- | --- |
| `SB_API_SERVER_URL` | `/api` | Base URL of the REST API. |
| `SB_SOCKET_SERVER_URL` | the page's own origin | Base URL of the Socket.IO server, without `/socket.io`. |

### End-to-end tests

The [Playwright](https://playwright.dev/) tests start their own server container with the dummy provider and a test build of the interface, on ports that don't collide with development (API 3200, SSH 6200, interface 4180).

The end-to-end tests currently don't run in CI. Start them by hand, or with the `e2e.yml` workflow.

```bash
# Once: build the server image in the antimony-server repository
docker build -t antimony-server:dev .

# Once: install the browser
npx playwright install chromium

yarn e2e          # headless, like CI
task e2e-ui       # interactive
task e2e-report   # open the last report
```

To test against another server image, set `SB_E2E_BACKEND_IMAGE=<image>`.

## Documentation

This site is built with [Astro](https://astro.build/) and [Starlight](https://starlight.astro.build/).

```bash
git clone https://github.com/antimony-team/antimony
cd antimony/site
npm install
npm run dev
```

| Path | Contents |
| --- | --- |
| `src/pages/index.astro` | The landing page |
| `src/content/docs/docs/` | The documentation pages, in Markdown and MDX |
| `src/components/diagrams/` | The diagrams, as Astro components with inline SVG |
| `openapi/antimony.swagger.json` | Copy of the server's Swagger file for the REST API reference |
| `plugins/release-version.mjs` | Fills in the version of the current release, see below |

Install commands and download links name the files of the current release, so that they can be copied as they are. Write <code>&#37;VERSION&#37;</code> where the version goes, in text, code or links. The build replaces it with the latest stable release from GitHub, or the newest pre-release while there's no stable one, and with `x.y.z` if there's no release or GitHub can't be reached. Set `ANTIMONY_RELEASE=0.2.0` to build with another version. The release workflow rebuilds the website after every release.

Update the REST API reference after the server's API changes:

```bash
npm run sync-api                                          # from GitHub
npm run sync-api -- ../../antimony-server/src/docs/swagger.json   # from a local checkout
```

## Continuous integration

| Repository | Workflow | Runs on | What it does |
| --- | --- | --- | --- |
| antimony-server | `ci.yml` | Pushes to `development` and `main`, PRs, tags `v*`, manually | Lint, Swagger check, build with a startup smoke test, tests with the race detector, then the Docker image |
| antimony-server | `fuzz.yml` | Nightly, manually | Fuzz tests |
| antimony-interface | `ci.yml` | Pushes to `development` and `main`, PRs, tags `v*`, manually | Lint, type check, unit tests, then the Docker image. Antimony Desktop (AppImage, .deb and .rpm for x86_64 and ARM64) is built on every run and kept as the artifact `antimony-desktop`. |
| antimony-interface | `e2e.yml` | Manually, or called by another workflow | End-to-end tests against `ghcr.io/antimony-team/antimony-server:dev` |
| antimony | `release.yml` | Tags `v*` | Builds Antimony Desktop from the interface at the same tag, packs the deployment files with that version, writes their checksums to `SHA256SUMS`, attests them, and creates the GitHub release with them |
| antimony | `docs.yml` | Pushes to `main`, PRs that change `site/`, manually | Builds this website and publishes it to GitHub Pages from `main` |

Both `ci.yml` workflows build the images for amd64 and arm64. Pull requests only build them. Pushes publish them as `:dev` (from `development`) or `:main` (from `main`), and tags as `:<version>`, `:<major>.<minor>` and `:latest`, under `ghcr.io/antimony-team/antimony-server` and `ghcr.io/antimony-team/antimony-interface`. Every published image contains an SBOM and its build provenance, and gets a [build attestation](/docs/deployment/docker/#verifying-downloads) signed by GitHub.

To release a version, tag `antimony-server`, `antimony-interface` and `antimony` with the same `v*` tag, in this order. The release in `antimony` checks that the images of that version exist. Its deployment archive and Antimony Desktop both start the images of that version.
