Next to the web interface, the Antimony server runs its own SSH server. It does two things:

- **Shells.** Connect to any node of a running lab from your own terminal, without knowing the node's address or setting up keys on it.
- **Packet capture.** Stream the traffic of any node interface to your machine as a pcap stream. Pipe it into Wireshark to watch the lab live, or into a file to analyse later.

You don't connect to the node itself. You connect to Antimony and tell it which node you want through the SSH **username**. Antimony then finds the node, whether it runs on the local Docker host or in a Kubernetes cluster.

<SshDiagram />

<Aside type="danger" title="Keep the SSH port on a trusted network">
	The SSH server currently does **not authenticate clients** and does **not check collection permissions**. Anyone who can reach the port can open a shell on, or capture traffic from, any node of any running lab.

	Only expose the port on a network you trust, or restrict it with a firewall. Don't publish it to the internet.
</Aside>

## Connecting

The server listens on `ssh.sshHost` and `ssh.sshPort` from the [configuration](/docs/deployment/configuration/#ssh). If your config doesn't set a port, the server uses **6969**. In the examples on this page, `antimony` stands for the host name of your Antimony server.

<Aside type="tip" title="Leave out the port">
	With a host entry in `~/.ssh/config`, `antimony` works as the host name as it is, and you don't need `-p 6969`:

	```ssh-config title="~/.ssh/config"
	Host antimony
	  HostName antimony.example.com
	  Port 6969
	```
</Aside>

### Choosing a node

The SSH **username** tells Antimony which node to use. It isn't an account: there is no password, and your local user name plays no role. Antimony splits the username at `/` and accepts these forms:

| Username | Where to find the parts |
| --- | --- |
| `<collection-name>/<lab-name>/<node-name>` | **The default.** The collection and lab names as shown in the dashboard, and the node name from the topology. The copy buttons in the interface use this form. |
| `<lab-id>/<node-name>` | The lab's UUID, shown in the lab info panel. |
| `<instance-name>/<node-name>` | The lab's instance name, shown in the lab info panel. It's the topology name, with spaces and underscores replaced by `-`, plus a 12-character suffix. It isn't the lab's display name. |
| `<container-id>` | The node's container ID, shown in the node panel. On containerlab, this is Docker's 12-character short ID; the full 64-character ID doesn't match. On clabernetes, it's the pod UID. |

- **With two parts**, a UUID as first part is read as a lab ID, anything else as an instance name.
- **Names must match exactly**, including upper and lower case.
- **Names with `/`** can't be used, since `/` separates the parts. If a collection or lab name contains one, use the lab ID instead.
- **Spaces** are fine, but the username then has to be quoted. Pass it with `-l "…"`.
- **Without a username** (`ssh antimony`), your SSH client sends your local user name, which Antimony reads as a container ID and doesn't find.
- **Four or more parts** are rejected with `invalid node`.

The lab must be running.

### Opening a shell

Connect **without a command** to get an interactive shell on the node:

```bash
ssh -p 6969 <collection-name>/<lab-name>/<node-name>@antimony

# Names with spaces
ssh -p 6969 -l "<collection-name>/<lab-name>/<node-name>" antimony
```

Antimony opens the shell the same way as the [browser terminal](/docs/manual/lab-view/#terminals): it first logs in to the node over SSH on port 22, using the username and password from [`kinds.conf.yml`](/docs/deployment/configuration/#node-kinds-kindsconfyml). If that fails, for example on a plain Linux container without an SSH daemon, it falls back to `bash` or `sh` inside the container.

The shell needs a terminal. OpenSSH requests one by itself when you run it from a terminal; only when its standard input isn't one, for example in a script, force it with `-tt`.

Terminal resizes are passed through. When you exit the node's shell, the SSH session ends.

<Aside type="note">
	Shells opened through the SSH server don't count towards the per-user limit and don't close on idle. Those limits (`shell.userLimit`, `shell.timeout`) only apply to browser terminals.
</Aside>

### Capturing traffic

Connect **with a command** to capture traffic. The command names the interface:

```bash
# Watch live in Wireshark
ssh -p 6969 <collection-name>/<lab-name>/<node-name>@antimony eth1 | wireshark -k -i -

# Read with tcpdump
ssh -p 6969 <collection-name>/<lab-name>/<node-name>@antimony eth1 | tcpdump -n -r -

# Save to a file
ssh -p 6969 <collection-name>/<lab-name>/<node-name>@antimony eth1 > capture.pcap
```

You don't have to type these. In the [lab view](/docs/manual/lab-view/#interfaces-and-capture), every interface of a node has a **Copy capture command** button, and the node's right-click menu has **Copy SSH command** and **Copy capture for &lt;interface&gt;**. They copy commands with the default username, like the first example above. The host is the one you opened Antimony with, and `-p` is left out when the server uses port 22.

#### Accepted commands

The command is either just the interface name, or a `tcpdump` command line. This means tools that run `tcpdump` remotely also work, such as Wireshark's built-in **SSH remote capture** (sshdump), whose default command is `sudo tcpdump -U -i <interface> -w -`. In its settings, enter your Antimony server and SSH port, put `<collection-name>/<lab-name>/<node-name>` in the username field and leave the password empty.

| Command | Result |
| --- | --- |
| `eth1` | Captures `eth1` |
| `tcpdump -i eth1 -w -` | Captures `eth1` |
| `sudo tcpdump -U -i eth1 -w -` | Captures `eth1`. A leading `sudo` is ignored. |
| `tcpdump -nUi eth1` or `tcpdump --interface=eth1` | Captures `eth1` |
| `tcpdump -i eth1 port 179` | Captures **all** traffic on `eth1`. Filters are ignored. |
| `ls` | Fails: Antimony tries to capture an interface called `ls`. |

Only the interface option is read; every other `tcpdump` option and any filter expression is ignored. To filter, apply a display filter in Wireshark, or pipe the stream through `tcpdump -r - <filter>` locally.

#### What you receive

- A standard **pcap stream** (Ethernet link type, snapshot length 65 536 bytes), starting with a pcap file header. Any tool that reads pcap from standard input works.
- **Shared captures.** If several people watch the same interface, Antimony captures it only once and sends a copy to everyone. The capture stops when the last viewer disconnects.
- **No back-pressure.** Each viewer has a buffer of 1 024 packets. If your connection can't keep up, packets are dropped for you instead of slowing down the capture for others.
- **Long-running.** The capture continues until you disconnect, the node stops or the server shuts down. Antimony checks every 10 seconds whether your session is still alive, so `ssh -n` and other sessions without input keep running.

## Excluded interfaces

`capture.excludedInterfaces` lists interface names that Antimony hides from the interface list and statistics in the UI, such as `lo`, management interfaces and the clabernetes underlay `c9s0`. Entries are glob patterns (`mgmt0*`).

<Aside type="caution">
	The exclusion list only hides interfaces in the interface. It doesn't stop anyone from capturing an excluded interface over SSH by name.
</Aside>

## Host key

On its first start, the server generates an Ed25519 host key at `ssh.sshKeyPath` (default `./key`, which is `/app/key` in the Docker image). If you don't keep that file, a new container generates a new key and SSH clients warn that the host key changed.

Keep the key across restarts and upgrades by storing it on a volume.

Mounting a directory is the easiest way to do this. Point `ssh.sshKeyPath` at a file inside it and the server creates the key there on the first start:

```yaml title="config.yml"
ssh:
  sshKeyPath: ./ssh/host_key
```

```yaml title="docker-compose.yml"
services:
  server:
    volumes:
      - ./mnt/ssh:/app/ssh
```

## Enabling and disabling

- `ssh.enabled: false` stops the SSH server from starting. Shells from your own client and packet capture are then unavailable. Browser terminals don't need the SSH server and keep working.
- `capture.enabled: false` keeps the SSH server running for shells, but rejects every capture command with `traffic capture is not enabled`. The node's right-click menu then leaves out its **Copy capture for &lt;interface&gt;** entries.

## Errors

The server writes errors to standard error and exits with code `2` for usage errors or `1` for other failures.

| Message | Meaning |
| --- | --- |
| `traffic capture is not enabled` | You sent a command, but `capture.enabled` is `false`. |
| `invalid node "…", expected …` | The username has four or more parts. Use one of the [usernames](#choosing-a-node). |
| `unable to connect to node: the specified node was not found` | No node matches the username. Check the spelling and case of the collection, lab and node names, or the ID. |
| `unable to connect to node: the specified lab is not running` | The lab exists but isn't deployed. |
| `a terminal is required for a shell, connect with ssh -t` | You asked for a shell without a terminal, for example from a script. Add `-tt`. |
| `missing interface to capture` | The command was empty. |
| `unexpected arguments [...], expected an interface name or a tcpdump command` | The command has several words but isn't a `tcpdump` command. |
| `the tcpdump command has no interface (-i)` | Add `-i <interface>`. |
| `node <lab>/<node> is not running` | The node is stopped. Start it from the lab view first. |
| `failed to capture <interface> on <lab>/<node>: …` | The interface doesn't exist or the provider refused the capture. On clabernetes, only link interfaces can be captured. |
