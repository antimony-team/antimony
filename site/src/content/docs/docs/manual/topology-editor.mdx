The topology editor is where you create and change [containerlab topologies](https://containerlab.dev/manual/topo-def-file/). It shows the same topology two ways at once: as YAML and as a graph. A change in one is reflected in the other.

## Collections

Topologies are organised in **collections**. A collection usually belongs to a class, a course or a team, and it decides who can see and use its topologies (see [permissions](/docs/deployment/authentication/#permissions)).

Administrators manage collections:

- **New collection**: right-click an empty area of the explorer.
- **Edit** / **Delete**: open the collection's **…** menu or right-click it.

Each collection has two switches:

- **Anyone can deploy**: everyone with access can start labs from this collection's topologies.
- **Anyone can edit**: everyone with access can add, change and delete topologies here.

<Aside type="caution">
	Deleting a collection asks for confirmation and lists the topologies it contains.
</Aside>

When you open the editor for the first time and no collection exists, it guides you through creating a collection and a first topology.

## The explorer

The left panel shows collections, their topologies and each topology's bind files as a tree. Type in **Search topologies** to filter it.

| Item | Buttons and menu |
| --- | --- |
| Collection | **+** adds a topology. The menu has **New topology**, and for administrators **Edit** and **Delete**. |
| Topology | **▶** opens the deploy dialog for it. The menu has **Deploy**, and for its creator and administrators **New file**, **Upload files**, **Edit** and **Delete**. |
| File or directory | The menu has **Edit** and **Delete**. |

Right-clicking an item opens the same menu.

**Drag and drop** a topology onto another collection to move it. Drag a bind file onto a topology or a directory to move it there.

### Creating a topology

Choose **New topology** on a collection. Give it a **Name** and optionally a **Sync URL** (see [Git sync](#sync-from-a-url)). The new topology starts empty:

```yaml
name: my-topology
topology:
  nodes: {}
```

## The editor

The toolbar shows the topology's collection and name. An asterisk marks unsaved changes.

| Control | What it does |
| --- | --- |
| **Undo** / **Redo** | Step through your changes. Also <kbd>Ctrl</kbd>+<kbd>Z</kbd>, and <kbd>Ctrl</kbd>+<kbd>Y</kbd> or <kbd>Ctrl</kbd>+<kbd>Shift</kbd>+<kbd>Z</kbd>. |
| **Code** / **Split** / **Graph** | Show the YAML, both, or only the graph. Your choice is remembered. |
| **Sync options** | Set the URL to sync the topology from. |
| **Save** | Save the topology. Also <kbd>Ctrl</kbd>+<kbd>S</kbd>. Disabled while the topology is invalid. A red dot means there are unsaved changes. |
| **Download** | Download the YAML as `<collection>_<topology>.yaml`. |
| **Deploy** | Open the [deploy dialog](/docs/manual/deploying-labs/) for this topology. |

If you try to leave with unsaved changes, Antimony asks whether to **Discard changes** or **Keep editing**.

### YAML

The YAML editor validates the topology against the containerlab JSON schema while you type, with completion and hover help for every field. The status bar at the bottom shows **Valid**, **Pending** or **Error**; hover over it to see the problem. It also shows the cursor position and the number of nodes and links.

Paths under `binds:` are links. Click one to open that bind file, or to create it if it doesn't exist yet.

### Graph

The graph shows nodes with their icons and the links between them, labelled with interface names. Drag nodes to arrange them; their positions are saved in the topology.

The toolbar on the left of the graph:

| Button | What it does |
| --- | --- |
| **Select** (<kbd>V</kbd>) | Select, move and resize nodes, groups, shapes and text. Shift-click adds to the selection. |
| **Hand** (<kbd>H</kbd>) | Pan the graph by dragging. |
| **Add node** | Opens the [node dialog](#the-node-dialog) to add a node. |
| **Rectangle** (<kbd>R</kbd>), **Ellipse** (<kbd>O</kbd>), **Line** (<kbd>L</kbd>), **Text** (<kbd>T</kbd>) | Draw shapes, lines and text on the canvas. |
| **Group** (<kbd>G</kbd>) | Draw a named group box. Nodes and shapes whose center it covers are put in the group. |
| **Group selection** (<kbd>Ctrl</kbd>+<kbd>G</kbd>) | Puts the selected elements in a new group. |
| **Fit graph** | Zooms to show the whole topology. |
| **Clear graph** | Removes all nodes. Can be undone. |

Topologies you can't edit only show **Select**, **Hand** and **Fit graph**. On macOS, use <kbd>Cmd</kbd> wherever these docs say <kbd>Ctrl</kbd>.

Click an element to select it. The bar above the selection has its style options and **Delete**. Double-click a node's icon to open the node dialog, or its name to rename it. Double-click a link to rename the interface at the nearer end, and a group's name to rename the group. Right-click nodes, links, groups, shapes and the background for more options.

To connect two nodes, right-click the first one, choose **Connect** and click the second one. Clicking the first node again connects it to itself. Antimony uses the next free interface on both ends. Press <kbd>Esc</kbd> or click anywhere else to cancel.

### The node dialog

The node dialog edits everything about a node:

- the **icon** (click it to choose one), **Name** and **Kind**
- **Node properties**: every containerlab node property, with search and validation from the schema
- **Connections**: the node's links and the interfaces they use
- environment variables, certificates, health checks, DNS settings, labels and more

## How the graph is stored

The topology file only describes the lab. Everything about how it looks in the graph lives in a separate **annotations file** next to it, `<topology>.clab.yml.annotations.json`. It uses [containerlab's annotations format](https://containerlab.dev/manual/topo-def-file/), the same one the containerlab VS Code extension and TopoViewer read, so the layout carries over to those tools and the topology stays a plain containerlab file. The server validates the annotations against containerlab's annotations schema when you save.

Use the **Topology** / **Annotations** file switch in the editor to view and edit the annotations as JSON. Antimony writes them whenever you change the layout, such as moving nodes, changing groups or drawing shapes and text.

| Section | Contents |
| --- | --- |
| `nodeAnnotations` | One entry per node, matched by `id` (the node name): its `position`, `icon` and the `groupId` of the group it is in. Nodes placed on a map use `geoCoordinates` instead of `position`. |
| `groupStyleAnnotations` | The group boxes: `id`, `name`, `level`, the `position` of the top left corner, `width`, `height` and optional styling such as colors and borders. A group with a `parentId` is drawn inside another group. |
| `freeTextAnnotations`, `freeShapeAnnotations` | Text, rectangles, circles and lines drawn on the canvas. |
| `edgeAnnotations`, `viewerSettings`, … | Other settings from the format. Antimony keeps them when it saves, even those it doesn't use. |

```json title="lab.clab.yml.annotations.json"
{
  "nodeAnnotations": [
    {
      "id": "leaf1",
      "position": { "x": 320.5, "y": 180 },
      "icon": "switch",
      "groupId": "fabric"
    }
  ],
  "groupStyleAnnotations": [
    {
      "id": "fabric",
      "name": "fabric",
      "level": "1",
      "position": { "x": 240, "y": 110 },
      "width": 320,
      "height": 160
    }
  ]
}
```

Available icons: `router`, `switch`, `spine`, `dcgw`, `server`, `client`, `controller`, `pon` and `rgw`. `pe` is an alias for `router` and `leaf` for `switch`. Nodes without an icon, or with an unknown one, are shown as `client`.

Nodes without a position, e.g. in a topology that was pasted, synced or only edited as text, are placed automatically. If no node has a position, the whole graph is laid out by its links. Otherwise, the other nodes keep their positions and the new ones are placed next to the nodes they are linked to. The same topology is always placed the same way, and the positions are only saved once you change the layout.

### Layout in labels (older topologies)

Antimony used to store the layout in containerlab `labels` on each node: `graph-posX`, `graph-posY`, `graph-icon`, `graph-group`, `graph-level`, `graph-geoCoordinateLat` and `graph-geoCoordinateLng`. These labels are deprecated in all containerlab tools. Antimony still reads them for nodes without an annotation, so older topologies keep their layout, but never writes them. As soon as you change the layout, the labels are removed from the topology and converted into annotations, with a group box created around the nodes of each former group.

## Bind files

Bind files are files that containerlab mounts into nodes, such as startup configurations. They belong to a topology and appear under it in the explorer.

- **New file**: create a file by its path, for example `configs/r1.conf`. Directories are created as needed.
- **Upload files**: upload an archive (`.zip`, `.tar`, `.tar.gz`, `.tgz`, `.7z`, `.rar`, `.bz2`). Antimony unpacks it in your browser and lets you pick which files to add. Existing files with the same path are marked and overwritten. A top-level folder named like the topology is removed.
- Click a file to edit it in the code editor, and use **Download** in the toolbar to download it.
- **Edit** renames or moves a file or directory. Deleting a file asks you to type its path to confirm.

Reference bind files in the topology with paths relative to the topology:

```yaml
topology:
  nodes:
    r1:
      kind: linux
      binds:
        - configs/r1.conf:/etc/frr/frr.conf
```

Bind file paths must stay inside the topology. Absolute paths and `..` are rejected. The [topology policy](/docs/deployment/topology-policy/#reading-files-from-the-server) also reports any file the topology refers to that isn't one of its bind files.

Some names are reserved because Antimony, containerlab or netlab create files with them in the topology's directory. A bind file can't be created if the first part of its path matches one of them, ignoring case. Otherwise it could overwrite the topology or the lab's certificate authority at deploy time.

| Reserved names | Used for |
| --- | --- |
| `topology.clab.yaml`, `topology.yml` and their `.annotations.json` files | The topology and its graph layout |
| `clab-*` | containerlab's lab directory, with the lab's state and certificate authority |
| `clab_templates`, `topology.clab_vars.*` | containerlab templating |
| `netlab.snapshot.pickle`, `netlab.snapshot.yml`, `netlab.lock`, `hosts.yml`, `ansible.cfg`, `group_vars`, `host_vars`, `node_files`, `clab_files`, `config` | Files netlab generates |

## Sync from a URL

A topology can be kept in sync with a file on the web, for example a raw file in a Git repository.

1. Open **Sync options** in the toolbar, enter the **Sync URL** and click **Save**.
2. Click **Fetch** to load the file into the editor.
3. Review the changes and **Save** the topology.

<Aside type="note">
	Your browser downloads the file, not the server. The URL must be reachable from your browser, allow cross-origin requests (CORS) and return a text content type. Raw file URLs from GitHub (`raw.githubusercontent.com`) work.
</Aside>
